Benchmarks

Every cross-language run, including the ones slang loses.

Markdown·llms.txt·api.json

slang is measured against C, Go, Rust, C#, Java, Python, Bun and Node.js by bench/suite: the same SQL, the same response contracts, the same dataset, and a conformance gate that runs before anything is timed — a language that fails to build or fails conformance is reported as failed, not measured, so a number here means the implementation actually did the work, not just that it ran.

Two tiers: light (raw HTTP connection handling, CPU + allocation throughput) and heavy (a Postgres-backed JSON API and a big-data batch job). Full contract in bench/SPEC.md. The full record below is reproduced verbatim from bench/RESULTS.md, including the runs where slang loses and the runs that are only partial.

RPS alone is not a win. A result worth trusting needs throughput considered alongside tail latency and memory together, measured on a dedicated host at the scale the SPEC calls for — not whichever single number happens to flatter one runtime. Benchmarks that quote only the number that flatters them are the reason nobody believes benchmarks.

Also measured #

Beyond the cross-language comparison, stress_test/ holds a scaling suite for slang on its own: request-count scaling from 10k to 100k, concurrency scaling to 2,000 connections, per-endpoint characterisation, a breaking-point probe, a soak test, CPU profiles, and a concurrent-task curve with no network in the way at all. Its write-up is stress_test/reports/stress_report.html.

Cross-language suite — results#

Two runs are recorded here, newest first. They ran on different hosts, so compare languages within a run, never one run's numbers against the other's.

Run 2026-11-23: full suite, both tiers#

The first run of the whole suite defined in bench/SPEC.md: the light tier (http-static, compute) and the heavy tier (a Postgres-backed JSON API, api, and a CSV aggregate, batch). Every language passed the conformance gate (bench/suite/lib/conformance.py) and the batch output check before anything was timed; no server died.

Languages: slang, Go, Rust, Java, Bun, Node.js. C# built but failed api conformance and its http-static server did not start on this host, so it was left out of the run rather than measured broken. C and Python were not run.

Read the host first. A shared-vCPU cloud VM with 4 vCPUs, which are 2 physical cores with 2 hyperthreads each. The suite's default split gives the server under test CPUs 0-1 (one physical core), the load generator CPU 2 and Postgres CPU 3, so those two share the other core. That is a quarter of the host bench/CURSOR.md asks for, and the run's own host check says so: Rust compute took 3,220 ms against the reference host's 1,577 ms, so summary.md marks the run not comparable with other hosts. CPU steal over the run was 0.0%.

What this run shows#

  • JSON with no database (api/quote) is the cleanest signal, with round-to-round spread of 3-8%: slang 5,592 req/s at 64 connections, Rust 5,183, Go 4,035, Bun 3,914, Java 3,601, Node 2,850. slang and Rust are level within noise; both are 24-38% ahead of Go.
  • Postgres-backed reads (api/point, api/mix) are database-bound. Postgres sat at 0.94-0.97 of its one core in every run but Node's, and rounds spread 17-39%, round 1 usually lowest. slang has the highest median in all four, but slang, Java, Go and Rust are within that spread of each other: read them as one tier, with Bun behind and Node clearly last.
  • At a fixed rate (wrk2), every language but Node holds the target of 2,000 and 10,000 req/s; at 10,000/s slang's p99 is 3.61 ms, Rust's 3.73, Go's 7.98. Node falls behind at 10,000/s (6,399 served, multi-second latency).
  • Batch: slang is 13% slower than Go and uses a fifth of the memory (9.6 s and 433 MB against Go's 8.5 s and 2.1 GB). Rust is fastest at 5.0 s. Spread 1-3% (Rust 10%).
  • Memory is consistent everywhere: slang's peak RSS is the lowest or second lowest in every workload, beside Rust and Go; Java sits at 700 MB+ in the API.
  • http-static measured the load generator, not the servers. One CPU of wrk tops out near 19,000 req/s; every server but Node lands within that band while using 1.1-1.5 of its 2 CPUs. Only the memory column separates them there.

Changes made to run on this host#

  • setup_host.sh installs the OS's Postgres where 16 is not packaged (18 on Ubuntu 26.04), and builds wrk2 with its Lua bytecode emitted as C: the bundled LuaJIT's ELF object is read as corrupt by 26.04's binutils, which left every fixed-rate run panicking on start.
  • bench/compute/cs/Compute.csproj targets net10.0, like the suite's other C# projects (the build failed with NETSDK1005). C# still failed conformance and was left out.
  • The slang programs read their settings with to_int instead of an extern fn atoi, and the API scans an id with for c in s instead of copying it to bytes. No implementation's logic, libraries or flags changed; slang's gains since the last run come from the compiler and runtime it was built with.

Earlier run 2026-09-17: light tier only (interim)#

This is a partial run, published early. It covers only the light tier (http-static, compute) of the suite defined in bench/SPEC.md: raw connection handling and CPU + allocation throughput, with no database and no JSON in the loop. The heavy tier (a Postgres-backed JSON API and a big-data batch job — the workloads that exercise a driver, a connection pool, and a JSON codec under load) was aborted partway through a ROUNDS=3 run to stop runaway compute spend, and is not included here. The 2026-11-23 run above is the first full run, heavy tier included.

The host was undersized for a publish-grade run. 4 vCPUs / 15 GiB RAM on Docker overlay storage, run via a Cursor background agent — well below the 16+ cores / 64 GiB+ / local NVMe, dedicated-host bar bench/CURSOR.md sets for a result meant to be trusted. Absolute numbers here (a 4-core box serving both the app and the load generator and Postgres on the same four cores) are lower and noisier than a dedicated box would give; treat rankings as a rough first read, not a final word.

Shown here: C#, Java, Go, Rust, Bun, Node.js, and slang. The suite also measures C and Python on every run (see the run's own results.json for those), but this page's comparison set is restricted to the seven above.

The suite gates every language behind a conformance check before measuring it (bench/suite/lib/conformance.py) — a language that fails to build or fails conformance is reported as failed, not measured, so a number here means the implementation actually did the work, not just that it ran. All nine languages passed the light-tier gate on this run.

http-static#

GET /, a fixed 200-byte body, wrk -c{50,200} -d30s --latency. Median of 3 rounds, sorted by req/s (fastest first).

Reading these numbers#

All seven are within a fairly narrow band on raw throughput at this scale — a few thousand req/s apart on a 4-core box is not a strong signal either way, and Node's lower numbers here are a known shape for its single-process baseline HTTP server under this harness, not a general Node.js finding. Memory is the more legible gap: slang, Rust, Go and C sit in single-digit-to-low-double-digit MB; Bun, Node, and Java's JIT-warmed footprint run into the hundreds. None of this substitutes for the heavy tier, which is where a driver, a connection pool, and JSON encode/decode under sustained load will separate these runtimes more than an empty HTTP response does.

Known gaps in this run#

  • Heavy tier not run. No api (Postgres-backed JSON service) or batch (big-data CSV aggregate) numbers exist yet for any language.
  • Java's api implementation failed conformance on this host (no bench.Main sources were present for the Maven build to compile) — irrelevant to the light-tier numbers above, which don't touch it, but it means Java's heavy-tier numbers aren't just missing, they're currently broken and need a fix before the next run.
  • Host is a 4-core cloud VM sharing its cores between the server under test, the load generator, and Postgres — see bench/CURSOR.md for why that matters and what a publish-grade host looks like.
