Twelve phases, three surfaces, zero crashes

HTTP through the Arcade demo server, raw TCP through a dedicated echo server, and pure in-process concurrency with no network at all — the same machine, one continuous run, every phase sampling RSS/CPU/thread count alongside its own throughput and latency.

HTTP

The Arcade demo server (demo/main.sl), mixed workload across eight endpoints unless noted — the same server demo/README.md's own Tier 9 → Tier 11 → cooperative-preemption numbers were measured against.

Request-count scaling · concurrency 200, mixed workload

Throughput holds a flat band (1,095–1,363 req/s) from 10k to 100k requests — no warmup climb, no long-run decay, 0 errors at every point.

Concurrency scaling · 50,000 requests, mixed workload

Clean through 250 concurrent. Past 500, p99 jumps an order of magnitude and errors climb — the queueing cliff this suite exists to locate, not a crash: the server logs stayed empty.

Per-endpoint characterization · concurrency 100

ping/json/counter are near-instant routing + (de)serialization; sleep parks a task rather than blocking a thread; cpu/alloc are deliberately expensive (prime counting, allocation pressure) and fanout (8-way spawn + chan) is the slowest by design — chan only completed 12,064 of its 20,000-request budget inside the 120s cap at ~100 req/s, a duration limit, not a fault.

Breaking-point probe · sleep endpoint

Errors are client-side timeouts under deliberate overload (3,000–5,000 concurrent against 8 real worker threads) — the server itself never went down; http_server_final.log ends with a clean goodbye!.

Soak · 60s sustained, concurrency 250

68,180 requests over a full minute at steady concurrency, 0 errors — the shape that matters for "does it stay up," not a burst.

Raw TCP

A dedicated echo server (programs/tcp_echo) with no HTTP framing at all — isolates net.* and the kqueue reactor from the demo server's own routing/JSON cost. Scaling phases use persistent connections (one dial per worker, many round-trips) — see the churn callout below for why.

Request-count scaling · persistent, concurrency 100

21.9k–30.1k round-trips/sec across 10k–100k requests, 0 errors throughout.

Concurrency scaling · persistent, 50,000 round-trips

Steady 20k–28k req/s through 500 concurrent connections, then a real cliff at 1,000: throughput drops to 10,158 req/s, p99 crosses 2.1 seconds, and 33 requests time out — 128 workers genuinely saturated, the TCP-side analogue of the HTTP cliff above.

Why request-count/concurrency scaling use -persistent, and churn is measured separately

A fresh TCP connection per request (the default load-generator mode) hits macOS's own ephemeral-port ceiling (~16,384 ports, net.inet.ip.portrange.first/last) well before the server does — confirmed directly: it reproduces even at concurrency 10, where server capacity obviously isn't the constraint, and the client fails with exactly connect: can't assign requested address. That's a client-side OS artifact, not a server bug, so scaling phases ride one persistent connection per worker instead.

Concurrent compute

No network at all — programs/concurrent_compute spawns N tasks, each doing real CPU work (prime counting) plus allocation, isolating the M:N scheduler and GC's own cost from net.*'s.

Throughput vs. task count

891 tasks/sec at 1,000 tasks, easing down to 637 at 20,000 — a smooth curve, not a cliff, and every run finished with active_tasks_after=0: clean drain, no leaked tasks.

Peak RSS vs. task count

9.6MB → 33.6MB from 1,000 to 20,000 concurrent tasks — sub-linear, well short of one-OS-thread-per-task territory. CPU utilization climbs from 615% to 722–736% (near this 8-core machine's ceiling) as more tasks give the scheduler enough parallel work to fill every worker.

Continuity with the published numbers

This suite tests the same Arcade server demo/README.md's own Tier 9 → Tier 11 → cooperative-preemption progression was measured against, at different concurrency points and with a different scenario mix — the two are not a rerun of each other, but they land in the same shape:

  • CPU-bound endpoints stay flat under load, not degrading further. demo/README found cpu/alloc pinned near 75–115 req/s from 25 to 600 concurrent clients; this run's isolated characterization (concurrency 100) lands at 102–107 req/s — the same ceiling, for the same reason (no calls or back-edges inside the hot prime-counting loop for cooperative preemption to interleave around as cheaply as elsewhere).
  • Cooperative preemption is genuinely active under this load, not dormant. sl_rt_maybe_yield/sl_rt_gc_checkin are real, sampled top-of-stack costs in both the HTTP profile (3,651 / 1,653 samples) and the compute profile (6,997 / 2,766) — matching demo/README's own finding that preemption shows up as measurable overhead precisely where it's supposed to.
  • The server never crashes under deliberate overload — it queues, and clients time out. Both the HTTP breaking-point probe (up to 21.4% client errors at 5,000 concurrent) and the TCP concurrency cliff (1,000 concurrent) end in clean, logged shutdowns, no different from demo/README's own "zero crashes, zero hangs" record across every prior re-run.

Methodology. One 8-core/16GB dev laptop, not a dedicated benchmark rig — treat absolute numbers as directional, the shapes (flat vs. climbing, where the cliff sits) as the real signal. Every phase samples the server process's own RSS/CPU%/thread count once per second (scripts/monitor.sh) so throughput can be read against real resource cost. Full raw output — every results/*.json, *.csv, compute_*.txt, and profile_*.txt — lives alongside stress_test/scripts/run_full_suite.sh, gitignored (fresh data every run, not meant to be committed).

Reproduce with cd stress_test/scripts && ./run_full_suite.sh — roughly 25 minutes end to end, twelve phases, no manual steps.
